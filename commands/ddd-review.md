# ddd-review

参数:`$ARGUMENTS`

第一个 token 是槽位名或编号,其余是单元名。不带单元则复核整个任务。

先加载 `ddd` skill。

---

## 必须在新会话跑

关键不是"谁写的代码",是**复核者不能持有实现时的上下文**。

刚写完代码的会话去复核自己的代码,会带着"我当时是这么想的所以没问题"的偏见。新会话只看得到 spec 和代码,它不知道也不需要知道实现过程中的纠结。

如果当前会话刚跑过 `/ddd-run`,直接告诉我需要换会话,不要勉强执行。

---

## 与 spec 验收的关系

不重复,维度不同。

| | spec 验收(`/ddd-run` 已做) | 本命令 |
|---|---|---|
| 问的问题 | 做的是不是要求的东西 | 这段代码本身有没有问题 + 有没有没说的事 |
| 执行者 | 实现者 | 独立会话 |
| 依据 | spec 的验收标准 | spec + 代码 |

spec 验收查不出的:并发安全、资源泄漏、错误被吞、性能陷阱、上下文未透传。代码可以完全符合 spec 且测试全绿,同时有个 data race。

---

## 阅读顺序(重要)

**先读需求,再读代码,然后 docs,最后才读 report。**

1. `requirement.md`、`spec.md`、`plan.md`、`context.md`
2. 改动的完整代码,以及被改动函数所在的整个文件、调用点、相关测试
3. `docs/`,按 `context.md`「参考文档」一节的索引取,只读与本次改动相关的
4. **最后**才读 `reports/`

这个顺序是本命令有效性的前提。先读 report 会被实现者的自述框住,你会顺着他的叙事去看代码,只能验证他说过的东西,发现不了他没说的东西。

而**他没说的东西恰恰是最有价值的发现**。

docs 排在代码之后是同一个理由:「参考文档」登记里产出者为单元号的,是实现者自己写的,同样会用他的叙事框住你。但它比 report 客观——它描述的是代码和环境,不是他的选择——所以可以早于 report。

产出者为 `人` 的调研材料,不受此限,想早读可以早读。

## 四个维度

### 一、代码质量

按优先级扫:正确性(并发、nil、边界、错误被吞、资源泄漏、上下文未透传)、安全、性能、可测性。

这个维度与 review 他人代码时完全相同,只加一条本流程特有的:**注释是否违反 skill 语言一节的代码注释规则**(emoji、修辞、markdown 强调符、出现本流程术语)。这一条不适用下方过滤的「格式」豁免,必须列出:出现本流程术语的按 major,其余按 minor。

理由:前三类是纯风格,但第四类会把任务级产物的引用永久留在代码里,归档之后无人能查证。

### 二、spec 符合性

对照 spec 逐条核:

- 契约层是否精确实现(字段名、类型、可选性、错误码)
- 行为层的边界条件和错误行为是否符合
- **「明确不做」的东西有没有被顺手做了**。这一项容易漏,而范围蔓延正是它要防的
- **实现是否偏离了 `requirement.md` 的技术方案**。spec 只写契约和行为,技术方案(同步还是异步、能力放在哪一层)不在 spec 里,所以这一项只能对照 requirement 核。它是实现者的前提,不该被静默推翻

### 三、未声明的偏离

**这是本命令独有的、也是最高价值的检查。**

整套流程的偏离传播机制,依赖实现者主动记录。但实现者可能压根没意识到自己偏离了。

所以:拿第二步形成的判断,对照 report 的偏离段。**代码里与 spec 不一致、而 report 没提的,全部列出来。**

对每条判定档位(定义见 skill 偏离一节):

- 局部 → 提示实现者补记录
- 跨单元 → **必须补进 `context.md`**,否则后续单元会基于错误前提工作
- 破坏性 → 停止,报告

### 四、跨单元一致性

复核整个任务时,额外检查:

- 各单元之间有无互相冲突的实现(不同 subagent 独立完成,这类冲突不会自己暴露)
- 是否有单元违反了 `context.md` 里已确立的事实
- 是否有单元改动超出了 plan 声明的范围

## 过滤

沿用 review 的过滤纪律:每条候选逐条过 gate,不过就删。

- **证据**:能否指向具体行证明问题存在。只能说"可能""建议考虑"的,删
- **前提**:结论是否依赖未知前提。**注意这一道在这里适用面小得多**,因为 spec 就是前提,大部分疑问查 spec 就有答案。真正查不到的才删
- **后果**:不改会发生什么。答案是"没什么"的,删。命名偏好、格式、linter 已覆盖的,一律删
- **归属**:是本任务引入的吗。存量问题删,除非本次放大了它
- **去重**:同一 root cause 只写一条,其余列位置

**少即是多。** 3 条有依据的发现好于 15 条正确但无用的。

## 产出

写入 `work/<槽位>/review.md`,并在终端输出摘要。

落盘的理由:未声明的偏离需要被后续动作处理,只在对话里说等于没说。`/ddd-sync` 会读它。

每条包含:

```
[severity: blocker|major|minor]
[维度: 代码质量|spec符合性|未声明偏离|跨单元一致性]
问题:一句话结论
位置:具体路径与行号,以及符号名
依据:触发路径,指向具体代码
建议改法:具体代码,不只描述
验收:改完之后怎么自证
```

severity 在这里的含义:

- `blocker`:不改不能发 MR
- `major`:应该改,不改会留下明确的后续成本
- `minor`:明确的小改进,可以不改

另外单独列出:

- **需补记录的偏离**,以及是否已写进 `context.md`
- **被 gate 拦下的项**,一行一条注明拦下原因。让我判断你是不是漏 review 了

## 不做的事

- 不修改代码。发现问题只报告,修由 `/ddd-run` 派单元去做
- 不修改 spec
- 不发布到任何远端。这是本地自查,发 MR 之后 review 同事那侧的事情不归它管
