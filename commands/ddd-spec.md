# ddd-spec

槽位:`$ARGUMENTS`

先加载 `ddd` skill。

---

## 本命令的形状

本命令**只负责进入任务并准备好上下文,然后停下**。需求由我在后续消息里描述,可以多轮,可以带链接。

产出两份文档,对应两个停下让我确认的点:

- `requirement.md` 回答「要解决什么问题、为什么这么解」,**允许模糊、允许有待确认项**
- `spec.md` 回答「要交付什么」,契约层不留白

分两步是因为方向没定的时候讨论字段类型是过早的。只有模糊方向时,第三步就是收敛方向的地方。

跑完之后:

- 不要猜我要做什么
- 不要"根据当前状态,我猜你可能想做 X"
- 不要给建议

那会污染澄清,我会不自觉地顺着你的猜测走。干脆地停在等待状态。

---

## 第一步:分流

槽位不存在 → 新建。存在 → 追加。**开口第一句就明确说走的是哪条**,不要让我猜。

⚠️ **参数是纯数字而没解析到任务时,直接报不存在,不要新建。** 编号只能用来指认已有任务,
新建必须给槽位名 —— 拿数字当名字会建出 `007-007` 这种没有含义的目录。

新建时编号自动补(**扫 `work/` 与 `archive/` 两处取最大值加一**),目录名为 `<编号>-<槽位名>`。

漏扫 `archive/` 会在归档后重新分配已用过的编号,让编号失去唯一标识作用。编号只增不复用。

---

## 第二步:前置检查

**新建:**

1. 确认涉及哪些仓库(不确定就问我),建立 `context.md` 的「涉及仓库」一节
2. 跑 `/ddd-upstream` 的逻辑,建立同步点基线
3. 读相关仓库的 `PROJECT.md`、`contracts.md`、`decisions.md`,以及 `cross-repo-decisions.md`
4. 检查 `contracts.md` 在途段有无占用

**追加:**

同上,外加读 `requirement.md`、`spec.md` 和 `context.md`,并**先输出当前状态摘要**:进行到哪、有哪些已确立的事实、哪些契约已定稿、`docs/` 下有哪些参考材料(路径 + 一句话用途,取自 `context.md` 的「参考文档」一节)。

这样我在描述新需求之前能看到已有约束,不至于提出跟已定契约冲突的东西;也能看到已经调研过什么,不至于让你重做一遍。

读 `context.md` 而非全部 report。report 是追加式历史,里面可能有已被推翻的陈述且没有标记。docs 同样只列索引不读全文,需要时再取。

---

## 第三步:需求收敛

**产出 `requirement.md`,这是第一个停下让我确认的点。**

本阶段回答"要解决什么问题、为什么这么解",不碰字段类型和错误码。方向还没定的时候去问契约细节是过早的。

三种入口:

- **只有模糊方向**:通过讨论收敛。技术方案在这一步讨论并落进「技术方案」一节:打算怎么改这个系统、涉及哪些模块、为什么这么选。它决定了后面会有哪些契约、拆出哪些单元,所以必须在 spec 之前定。实现细节不写(边界见模板)
- **产品已给需求文档**:用自己的话重述,不要复制粘贴。重述才有校验价值。原文档记链接
- **需求明确且改动很小**:写短一点,但不要跳过。这是我确认你理解正确的最便宜的检查点

允许留「待确认」项。requirement 是收敛过程的载体,不要求一次到位。

写完停下让我确认,不要自行进入下一步。

---

## 第四步:契约澄清

确认 requirement 之后才进入这一步。

**本阶段的主体是提问,写作是提问结束后的自然产物。**

如果我说完需求你立刻输出一份 spec,那份 spec 里所有没说清的地方都会被你用合理的猜测填满,而我看不出哪些是我说的、哪些是你猜的。

提问围绕契约层和行为层的留白展开(三层结构见 skill Spec 的三层一节)。**不要问实现细节。**

**写之前必须把推断的部分单列出来让我确认。** 格式类似:

```
以下是我的推断,请确认:
1. 你没提上传,我推断本期只做读
2. 你说"支持默认值",我推断它是配置项而非硬编码
```

链接读不到时**明说读不到并要我粘贴内容**,不要绕过去凭其余描述硬写。

---

## 第五步:写 spec

用 `projects/<主仓库>/templates/spec.md`。跨仓库任务用主仓库的模板,判断不了就问我。

三层结构见 skill Spec 的三层一节。要点:

- 契约层不留白,精确到可直接复制
- 行为层无歧义,但不规定怎么做
- **实现层沉默**
- 验收标准要厚,可执行,好的实现都能过、坏的都过不了、但通过路径不止一条
- 「明确不做」通常是最该认真写的一节

写完自检:换一个完全没参与讨论的开发者,能否不问任何问题产出通过验收的实现?必须来问说明契约层有洞;毫无决策空间说明写进实现层了。

---

## 第六步:登记

契约变更登记进对应仓库 `contracts.md` 的在途段,标注任务 ID。

跨仓库任务在每个涉及仓库的 `contracts.md` 里各登记一条。

---

## 过程中产生的其他文档

澄清阶段常会产出调研记录、现状梳理、资料链接清单。这些**不要塞进 `requirement.md` 或 `spec.md`**——前者会让需求文档变成调研报告,后者会稀释契约层。

一律写进 `work/<槽位>/docs/`,并登记进 `context.md` 的「参考文档」一节(格式见 skill 模板)。归属边界见 skill「法定产物与其他文档」一节。

`docs/` 首次写入时再建,不预建空目录。

---

## 追加流程的额外规则

**先定位当前状态**,处理方式完全取决于进行到哪一步:

| 状态 | 处理 |
|---|---|
| spec 未定稿 | 直接并入 |
| 已定稿未开工 | 改 spec,重跑自检和登记 |
| 已开工 | 进入影响评估 |
| 已完成待归档 | 默认建议开新任务 |

**影响评估**分三种:

- 纯新增,不动已有契约 → 追加进 spec,`/ddd-plan` 补单元
- 修改已定稿契约 → **停止报告**
- 推翻某个决策 → **停止报告**

停止报告时要列出:受影响的已完成单元、在途条目、以及**该契约是否已合并 master**。这一条决定处理方式:

| 契约是否已合并 | 处理 |
|---|---|
| 未合并 | 改原 spec,重跑 `/ddd-plan`。未合并的东西没有对外承诺,改它的成本远低于叠加一层 |
| 已合并且有外部依赖 | 新开任务,走正常契约演进 |
| 已合并但确认无人依赖 | 我来决定,你只报告不选择 |

**追加内容若改变了问题定义或方案取向,`requirement.md` 也要更新。** 纯粹的契约细化则只动 spec。

**改 spec 时保留痕迹。** **原地修改,不产生 v2 文件。** 版本历史在 git 里,而始终要有一份东西回答"现在的要求是什么";多一个版本文件就多一次让后续角色读错的机会。

在「变更记录」一节写明时间、内容、原因,不需要保留旧内容。它的用途是给读 report 的人对时间:已有 report 是基于旧版 spec 写的,没有变更记录,后续读到 report 和 spec 对不上时就是一个查不出原因的分叉。

**被推翻的 report 标记为 superseded,不删除。**

**同一槽位反复追加多次时提醒我一句,建议拆任务。** 反复追加通常意味着任务边界一开始就划错了,或者需求本身还没想清楚。不硬拦。

**契约变更是更新在途条目,不是新增一条。** 同一任务对同一契约的多次修改合并成一条,否则 `contracts.md` 会被同一任务的历史刷屏,而它必须保持薄。

**不允许自动改在途条目后继续。** 必须先报告给我。
