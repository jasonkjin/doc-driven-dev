# ddd-upstream

任务:`$ARGUMENTS`

先加载 `ddd` skill。

---

## 定位

**这是过滤器,不是同步器。** 主要产出应该是"本次无影响",偶尔才是"发现冲突"。

它也是**外部冲突的唯一有效防线**。`contracts.md` 的在途登记只对我自己的多任务并行有效,同事不用这套流程,看不到我的登记。所以别人的改动只能靠这里发现。

因此:`/ddd-spec` 开始前、发 MR 前必须跑;日常开工建议跑。

---

## 作用对象

本命令参数是槽位名,但它内部处理两个不同层次的东西:

- **拉取与粗筛是仓库级的**:git fetch、commit 范围、契约面路径
- **影响判断是任务级的**:关注路径、spec 前提、在途条目

因此:

**同步点按「任务 + 仓库」记录**,写在任务 `context.md` 里。不是按仓库全局记录。

理由是同一个仓库可能被多个任务关注,各自进度不同。共用一个全局同步点的话,先跑的任务会把它推进,后跑的任务永远看不到中间那段改动。代价是同一仓库会被不同任务重复 fetch 和粗筛,这个开销可以接受。

**对 `contracts.md` 已生效段的更新必须幂等。** 另一个任务可能已经把同一条契约标记过了,追加前先查,不要产生重复条目。

---

## 范围

读任务 `context.md` 的「涉及仓库」,对**每个仓库分别处理**。

**必须用「上次同步点 → 当前」的 commit 范围,不能只 diff 当前 HEAD。** 中途被引入又改回去的变更,在 diff 里看不见,而那类改动往往正是最需要知道的。

拉取时用 `repos.md` 里声明的默认分支,不要猜。`master` 与 `main` 混用很常见,拉错分支会静默地什么都发现不了。

首次跑没有同步点时,建立基线即可,不回溯。

---

## 两轮筛选

**粗筛,只看文件路径,不读内容。** 命中以下任一才进入细读:

- `PROJECT.md` 声明的契约面
- 任务 `context.md` 声明的关注路径
- `contracts.md` 在途条目涉及的文件
- **任务 `context.md`「参考文档」一节里各条目声明的「覆盖的代码路径」**

四者都不命中的直接判为无关,只统计数量。大仓库里这一步应该砍掉绝大部分。

**细读,只读命中的。** 判断:

- 是真的契约变更(签名、字段、语义、错误码),还是只是内部实现调整
- 是否与我在途的契约变更冲突
- 是否让当前 spec 的某条前提失效
- 只由第四条命中的,判断它是否让某份 docs 过期(见下)

---

## 四档产出

| 档 | 动作 |
|---|---|
| 无关 | 只更新同步点,一行输出 |
| 契约已变但不影响本任务 | 更新对应仓库 `contracts.md` 的已生效段 |
| 影响本任务但不影响 spec | 更新任务 `context.md`,输出提示 |
| 与在途契约冲突,或 spec 前提失效 | **停止,报告,不自行修改 spec** |

最后一档必须硬停。spec 是我审过的东西,被无声改掉我就失去了流程的控制点。

**别人的改动只更新已生效段,不能碰在途段。** 在途是我自己的占位登记,只有登记者能改。

---

## docs 过期标记

第四条命中源命中之后:**在该文档首部加一行 `STALE` 标记并在输出中报告,正文一个字不改。**

标记形如:

```
> ⚠️ STALE:2026-08-11 检出上游改动 api-service a1b2c3d 触及 handler/user.go,
> 本文基线 0e1f2a3 之后的内容未核对。
```

**机械漂移(行号位移、符号改名、文件移动)与语义变化(链路变了、结论不成立)一视同仁,都只标记。**

不为机械漂移开自动同步的口子,三个理由:

1. 任务级文档本来就明写「允许过期」,不值得为它让本命令变成会改文件的工具
2. 本命令的定位是过滤器,不是同步器。自动重写会破坏这个定位
3. 与 `/ddd-audit` 那条「自动修正文档等于把代码里的意外变更追认为事实」同源

同一份文档已有未处理的 `STALE` 标记时,**更新那一行而不是叠加一行**。同一仓库会被多个任务的本命令重复扫到,叠加会让文档头部长出一串标记。

`docs/` 或「参考文档」一节不存在时跳过这一步,不报错。

---

## 输出

按仓库分组,先给结论(有无冲突、能否继续),再给细节。无关的那部分只报数量,不要逐条列出。
