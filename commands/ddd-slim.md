# ddd-slim

任务：`$ARGUMENTS`

先加载 `ddd` skill，按其「槽位名解析」定位任务；只处理 `work/` 下的任务，不碰 `archive/`。
读主仓库的 `projects/<repo>/templates/` 模板实例：**重写后的法定产物必须仍符合模板的章节结构**（节名与节的职责不变，只删内容）。

---

## 作用

任务跑久了，文档会按时间层层叠加：就地改正的说明、被推翻的方案、逐轮复核的往返、早已完成的开工前置、过期的状态快照。
读者每读一节都要先读错的、再读为什么错，才读到对的那句。本命令把任务文档**重写成当下正确的形态**。

它执行的是 `ddd` skill 第二节「只记当下正确的结论，不记它是怎么变成正确的」，对已经积累的存量做一次性回收。

**硬约束：瘦身不得改变文档的效果。** 效果指：
- 下游命令（`/ddd-plan`、`/ddd-run`、`/ddd-review`、`/ddd-load`）读到的契约、判据、单元、已确立事实**不变**；
- 解析这些文档的机器（哨兵脚本、测试夹具）**照常工作**；
- 读者据此做出的判断**不变或更准**，不会更差。

删的是**叙述**，不是**信息**。拿不准一句话是哪一类时，保留。

---

## 范围

**做**：任务工作区 `work/<task>/` 下的 `requirement.md`、`spec.md`、`plan.md`、`context.md`、`review.md` 与 `docs/` 下的文本文档。

**不做**：

| 对象 | 为什么 |
|---|---|
| `reports/` | 执行记录不是交付文档，不受「只记当下」约束；且可能被脚本当输入 |
| `projects/<repo>/decisions.md`、`contracts.md` 已生效段、`cross-repo-decisions.md` | 仓库级决策只追加不覆盖（`ddd` skill 不变量 5） |
| 业务仓库的代码与注释 | 不在本命令范围 |
| 已发布 artifact 的源文件、原始材料（PRD 导出、转写、`.base` 导出）、回滚基线数据 | 删了就无法再更新 / 回滚；过时就在索引里注明，删不删问人 |
| 正在跑 `/ddd-sync` 归档的任务 | `/ddd-sync` 明令归档前不清理 `docs/`，归档不是删除。瘦身只在任务仍活跃时做 |

## 步骤

### 1. 备份与基线（动手之前）

1. **备份整个任务目录**（`~/ddd` 在 git 下时，先提交一次作为回滚基线即可；不在 git 下时没有备份就没有回滚）：
   `tar czf ~/ddd/.backup/<task>-pre-slim-<日期>.tgz -C ~/ddd/work <task>`。在输出里报路径。
2. **找出机器消费者**：`grep` 任务目录下的脚本（`docs/*.py` 等）与测试里引用了哪些文档、解析了哪些锚点
   （表头、标题行、固定前缀）。把这些锚点列成清单 —— **重写时逐字保留**。
3. **跑一遍这些消费者，记下基线输出**（例如 `21/21`、`49/49`）。
4. **留一份法定产物的原稿副本**到 scratchpad，供第 5 步对比。

### 2. 核实当下真相（不从旧文档抄状态）

文档里的状态类信息最容易过期。重写前先取证：
- 分支 HEAD、坐落基线、是否已推送、backup ref（`git rev-parse` / `merge-base` / `for-each-ref`）；
- 单元是否完成（`reports/` 是否存在）、哪些被后续单元取代；
- 部署版本、在途 MR 状态、开放项是否已关闭；
- 文档之间互相矛盾的地方，**以代码与 git 为准**判定哪边对。

### 3. 通读，再分类

**每份要改的文档全文读完再动笔**，不凭摘要或记忆重写。逐段归类：

| 类 | 例子 | 处理 |
|---|---|---|
| **当下契约与事实** | 接口、取值、逐字文案、判据、字段矩阵、平台常量、坑的结论 | **保留**，措辞去掉日期与过程 |
| **禁令** | 「不要做 X，会 Y」、被否方案作为「不走的路」 | **保留**，压成一句禁令 + 一句理由 |
| **理由** | 为什么这么定、代价是什么 | 保留结论性的理由，删推导过程 |
| **过程叙述** | 「原写 X 已作废」「2026-xx 就地改正」「第三轮复核发现」「此前以为」「改了两版」 | **删**，只留改正后的那句 |
| **执行记录** | 逐轮联调 / 部署执行日志、依赖图与执行顺序（单元已全部完成时） | **删**；其中仍有效的配方、坑、已通过项提炼进对应正文。spec 的变更记录节另有规则（第 4 步） |
| **已完成的开工前置** | 见下 | **按类型分开处理**，不整块删 |
| **过期状态** | 已关闭的待确认、已完成的在途依赖、被替换的部署版本、旧 token | **删**或改成当下状态 |
| **错误结论** | 与代码 / 已交付行为不符的描述 | 核实后**改成对的**（见第 5 步的停止条件） |

**已完成的开工前置怎么处理**：先分两类。

- **环境 / 外部前置**：在代码之外改过的东西 —— 权限授权、平台配置、DDL、数据迁移、配置中心 / 环境变量、带外审批。
  🔴 **保留，每条一行**：做了什么、当前状态、可查的凭据（审批单号、配置 key、表名、日期）。
  理由：代码和 git 里都读不出来；换环境（上生产、新环境、回滚重建）时要照着再做一遍；排障时要能确认「这一步做过没有」。
  放进 `context.md`「仓库理解」下的环境事实小节，不留在 `plan.md`。
- **流程前置**：先跑某个命令、从哪个分支开工、等某个 MR 合入、单元之间的先后。
  **删**：完成后不再约束任何人；仍有效的纪律（如「同一仓库同一时刻只派一个 agent」）提炼进 `plan.md` 执行纪律。

判不清属于哪类时，按环境前置保留。

### 4. 按产物重写

- **`spec.md`**：章节按模板（背景 / 契约变更 / 行为 / 明确不做 / 验收 / 变更记录）。保留全部契约节与判据表；
  **判据编号一个不动**（reports 与 plan 引用它们），推后的编号继续保留不回收。删开工顺序、「现状 / 已解除」类时效段。
  🔴 **变更记录不整节删**：模板要求它登记定稿后**对读者有影响的契约 / 行为变动**。瘦身成每条一行「日期 · 改前 → 改后 · 原因」，
  只删其中的措辞调整、思路修正、被否写法与复核往返（模板本就要求这些就地改、不留痕）。
  spec 状态标记（在途 / 已生效）与 `contracts.md` 不一致时不自行改，按 `/ddd-plan` 的口径报告。
  🔴 **大段逐字内容（tool description、文案表、判据行、代码块）不要手抄**：用「骨架 + 按原稿行号引入」的方式拼装
  （骨架里写 `@@INC a-b@@`，脚本从原稿副本展开），只对需要改写的行手写。手抄长串必然引入不可见的差异。
- **`requirement.md`**：问题、目标、非目标、方案取向、**仍开放的**待确认。已答的待确认把答案落进正文或 spec 后删掉编号。
  🔴 **被否决的替代方案及理由必须保留**（压成禁令即可）：代码里读不出来，是 `/ddd-sync` 的高质量提升候选。
- **`plan.md`**：单元全部完成时压成「单元表（有效 / 被取代 / 作废 + 一句内容）+ 判据覆盖表 + 不排单元的」。
  完成状态仍以 `reports/` 为准；单元的做法与偏离留在 report，不在 plan 复述。仍有未完成单元时，只压缩已完成部分。
- **`context.md`**：🔴 **四个模板节名一字不改**：「涉及仓库」（`/ddd-load`、`/ddd-upstream` 读）、「仓库理解」、
  「本任务内已确立的事实」（`/ddd-run` 写入、`/ddd-sync` 读取）、「参考文档」（`/ddd-load` 对账、`/ddd-plan` / `/ddd-review` 取用）。
  主题小节只能挂在这四节之下，不能另起并列的顶层节替代它们。
  - 「本任务内已确立的事实」**每条保留来源单元标注**（如 `（T54）`）；被后续单元推翻的直接改或删。
  - 「涉及仓库」的**关注路径不得收窄**（它决定 `/ddd-upstream` 的粗筛范围，写窄了会漏检）。
  - 删旧编号对照这类只为兼容旧引用存在的内容 —— 前提是其他文档里的旧编号引用已一并清掉。
- **`review.md`**：它是复核产出，不重写结论；只修正**已经不成立**的陈述（已收口的发现标明由哪个单元收口），删指向已删文件的引用。
- **`docs/`**：
  - **删**：已被法定产物吸收的调研、被后续文档取代的交接稿、快照、复核存档、已全部完成的工作清单。
    🔴 删之前把其中**跨任务仍有效的结论**（尤其「看起来能这么做但实际不行」）记进 `context.md` 归档待办，供 `/ddd-sync` 提升；原文在备份里；
  - **瘦身**：仍有用的参考材料（去掉过期段、保留可复用的配方 / 改动方案 / 取证方法）；
  - **保留原样**：脚本、原始材料、回滚基线；
  - `STALE` 标记只在该文档已**对照当前代码重写**后才去掉，否则保留。

### 5. 停止条件（发现以下情况时不自行改，列出来给人判）

- 重写会改变**契约取值或对外可观测行为**（文案、字段、错误码、判据的期望值）；
- 两份文档矛盾且代码也判不出谁对；
- 某句话删了会让一条仍在生效的禁令或风险消失，而你不确定它是否仍在生效；
- 文档描述的**行为**与代码实际行为不符 —— 可能是代码错了，这是未声明偏离，归 `/ddd-review` 判，不在这里「以代码为准」改文档（同 `/ddd-audit`：自动修正文档等于把代码里的意外变更追认为事实）。

**只有与行为无关的事实性错误**（符号在哪个仓、文件路径、计数写错、引用了已删除的步骤、状态快照过期）**直接改正**，并在输出里单列。

### 6. 引用卫生

- 对被删除或改名的文件、被改名的小节，`grep` 整个 `~/ddd` 与记忆目录，**逐处修正**（`reports/` 除外）。
- 更新 `context.md`「参考文档」索引，🔴 **保持模板五列** `| 路径 | 用途 | 覆盖的代码路径 | 基线 | 产出者 |`：
  删除的去掉；瘦身的更新用途与基线，「覆盖的代码路径」照实填（`/ddd-upstream` 靠它粗筛），产出者不变。
  索引与 `ls docs/` 两个方向都要对得上（`/ddd-load` 的对账口径）。
- 旧编号式引用（「事实 N」「待确认 N」「§x.y」）在留下的文档里要么指向仍存在的位置，要么改成直接陈述。

### 7. 验收（全部过了才算完成）

1. **机器消费者**：第 1 步的每个脚本重跑，输出与基线一致。
2. **判据零丢失**：新旧 `spec.md` 的判据编号集合取差集，必须为空。
3. **逐字内容零误丢**：对新旧法定产物抽取单行内较长的反引号字面量（如 ≥35 字符）取差集，**逐条过目**：每条消失的都要能说出是「过程叙述里的」或「已改正的错值」，否则补回。
4. **无悬空引用**：`grep` 已删文件名与旧小节名，除 `reports/` 外零命中。
5. **过程措辞残留**：`grep -E "原写|已作废|就地改正|推翻|更正|此前|原先|第[一二三四]轮|20[0-9]{2}-[0-9]{2}-[0-9]{2}"`，逐条判断剩下的是契约 / 数据基线 / 禁令理由，不是叙述。
6. **结构符合模板**：`context.md` 四个节名都在、参考文档五列；`spec.md` 节名符合模板；`plan.md` 里被取代 / 作废的单元仍有标注（`/ddd-run` 靠它决定不派发）。
7. 记忆里指向本任务文档的条目，路径与状态仍然成立。

## 输出

先给结论，再给细节：

- 备份路径；
- 每份文档的行数前后对比与一句话说明删了什么类；
- 删除的 `docs/` 文件清单（一行一个，附原因类别）；
- **清洗中改正的事实性错误**（逐条：原来怎么写、核实依据、改成什么）；
- **停下来需要人判的**（第 5 步命中的项）；
- 验收结果（每个机器消费者的输出、判据差集、悬空引用检查）；
- 刻意没动的对象与理由。

完成后停下，不主动做后续动作。

🔴 spec 与 requirement 是人审过的控制点。输出里要给出这两份的**语义差异摘要**（哪些节删了什么类内容、改正了哪几处），
让人能在不逐行 diff 的情况下确认没有契约被无声改掉。
