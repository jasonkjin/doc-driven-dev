# DDD 共享概念

本 skill 只定义**概念和产物形状**,不定义流程。流程在各个 `/ddd-*` 命令里。

所有 `/ddd-*` 命令都应显式加载本 skill,以保证对同一概念的理解一致。

---

## 一、核心前提

**项目状态存在磁盘上,不存在会话里。**

Agent 是随时可重建的角色,不是需要小心维护的长会话。开工先读文档恢复认知,干完把结果写回文档。

由此推出一条贯穿所有命令的要求:**任何有价值的产出必须落盘。** 只存在于对话里的结论等于不存在。

这个设计的代价是风险从"会话丢失"变成"文档与代码悄悄分叉",所以文档的正确性是硬要求,而不是尽力而为。

## 二、文档分层

### 慢变 vs 快变

| | 存什么 | 放哪 |
|---|---|---|
| 慢变事实 | 契约面在哪、生成产物是什么、验收怎么跑、禁区、反直觉约定 | `projects/<repo>/PROJECT.md` |
| 快变状态 | 当前契约总账、决策记录、任务进展 | `contracts.md` / `decisions.md` / `work/` |

混在一起的后果是 `PROJECT.md` 变成变更日志,然后腐烂。

### 仓库级 vs 任务级

| | 仓库级 `projects/<repo>/` | 任务级 `work/<task>/` |
|---|---|---|
| 正确性 | 必须长期正确 | 允许不完整、允许过期 |
| 范围 | 只覆盖耦合点 | 只覆盖本任务碰到的部分 |
| 生命周期 | 永久 | 随任务归档 |
| 写入姿态 | 克制,默认不写 | 随便写 |

任务级可以随意,因为有明确生命周期,过期不伤害任何人。仓库级必须克制,因为永久存在。

**仓库级文档的价值完全建立在它薄这个前提上。**

### 法定产物与其他文档

任务工作区里有六个**法定产物**:`requirement.md`、`spec.md`、`plan.md`、`context.md`、`reports/`、`review.md`。它们各自被某条命令依赖,位置和内容都不能挪。

其他一切文档——调研、参考、测试方案、草稿、资料清单——**一律落在 `work/<task>/docs/` 下**,并登记进 `context.md` 的「参考文档」一节。不登记的文档等于不存在,没有命令会发现它。

**以下内容进 `docs/` 一律算错放:**

| 内容 | 必须在 | 谁依赖它 |
|---|---|---|
| 问题定义、目标、技术方案 | `requirement.md` | `/ddd-plan` 据此拆单元 |
| 契约定义、行为规格、验收标准 | `spec.md` | `/ddd-run` 据此下沉验收 |
| 单元划分、依赖、范围 | `plan.md` | `/ddd-run` 据此派发 |
| 单元执行结果与偏离 | `reports/` | `/ddd-run` 判档的唯一依据 |
| 本任务内已确立的事实 | `context.md` | 偏离传播机制的载体 |
| 长期决策及理由 | `decisions.md` / `PROJECT.md` | `/ddd-load` 无条件读 |

判据:

**`docs/` 全删掉,流程仍能正确跑完,只是慢一点;法定产物删掉,流程会跑错。**

这条防的是把 `docs/` 用成逃生舱:技术方案写进 `docs/方案.md` 而不是 `requirement.md`,`/ddd-plan` 就拆不出单元;契约写进 `docs/接口设计.md` 而不是 `spec.md`,`/ddd-run` 就没有验收可下沉。两处被架空,整条链就断了。

`docs/` 是任务级的,沿用任务级的姿态:允许不完整、允许过期、随便写、随任务归档。**不设仓库级 `docs/`**,仓库长期知识仍归 `PROJECT.md` 与 `decisions.md`。

### 一条覆盖所有文档的原则

**只存代码里读不出来的东西。**

决策的理由、在途的变更、踩过的坑、"看起来能这么做但实际不行"的约定。凡是能从代码推断的,不要镜像一份到文档里。代码本身就在那里,agent 随时可以读,复述一遍是纯粹的负债,而且必然会过期。

这条是大仓库下整套体系能成立的关键。

### 另一条覆盖所有文档的原则

**只记当下正确的结论,不记它是怎么变成正确的。**

- 结论错了**就地改成对的** —— 不加更正段、不留原结论、不写「原写 X,实为 Y」、不留删除线
- 踩过的坑只留一句 **「不要做 X」**,不留为什么踩、当时怎么想的、改了几轮
- 被否决的方案、中间尝试、评审往返,一律不进交付物

例外只有一种形态:**写成禁令的「不要做 X」**(`requirement.md` 的否决方案、`decisions.md` 的取代关系、`PROJECT.md` 的反直觉约定)。它回答"以后别再这么干",不是"我当时怎么想的"。`reports/` 是执行记录不是交付文档,不受本条约束。

代价是读者每读一节都要先读一遍已作废的错误结论、再读一遍它为什么错,才读到对的那句;三节之后就开始跳读,而跳读的人会漏掉真正重要的那节。版本追溯归 git 与 `reports/`,不占正文。

自检:**这句话是在告诉读者现在该怎么做,还是在告诉他我是怎么想明白的?后者删。**

### 日常写与改文档时的做法

上面两条原则在每一次写入时执行,不攒到最后清理。所有 `/ddd-*` 命令写文档都照做:

**改结论**
- **就地替换,并改全所有副本。** 同一结论常在 spec、context、docs、skill 提示词里各有一份,改一处前先 `grep` 找齐,一次改完。只改一处会留下互相矛盾的两份,读者分不清哪份作数
- **状态是覆盖不是追加。** 分支 HEAD、部署版本、开放项、待确认,写新值时删旧值;「上一轮状态」「原来是 X」不留
- **待确认答了就落地并删编号。** 答案写进正文或 spec,不留「✅ 已答」的空壳;编号式引用改成直接陈述

**写新内容**
- **按主题放进已有的节,不按时间追加新段。** 不写「2026-xx 追加」「本轮新增」这类标题;日期只出现在数据基线、凭据与 spec 变更记录里
- **一条信息一个归属。** 按第二节「法定产物与其他文档」的表放,不在两份文档里各写一遍;需要时引用
- **法定产物的节名与结构不改。** 节名是其他命令的读写锚点(如 `context.md` 的「本任务内已确立的事实」、参考文档五列)。主题小节挂在模板节之下
- **已确立的事实标来源单元**,被推翻时直接改或删

**前置与过程**
- **开工前置完成后按类型处理**:在代码之外做过的改动(授权、平台配置、DDL、数据迁移、配置中心 / 环境变量、带外审批)写进 `context.md`「仓库理解」的环境事实,每条一行「做了什么 · 状态 · 凭据」;流程性前置(先跑哪个命令、等哪个 MR、单元先后)完成即删,仍有效的纪律提炼进 `plan.md`
- **执行日志不进交付文档。** 逐轮联调、部署过程写进 `reports/`;交付文档只留提炼出的配方、坑的禁令和当前结果
- **spec 变更记录每条一行**:日期 · 节 · 改前 → 改后 · 原因。只登记对读者有影响的契约 / 行为变动,措辞修正不登记

**docs**
- 调研结论被法定产物吸收后,在参考文档登记里写明「已并入 X」;被后续文档取代时写明取代关系。**是否删除由 `/ddd-slim` 统一判断**,归档前不单独清理(`/ddd-sync` 的约定)

存量已经臃肿时,跑 `/ddd-slim` 做一次性回收。

## 三、契约

### 定义

**契约是改动之后会让别人跟着改的东西。**

具体范围由每个仓库的 `PROJECT.md` 声明,因为不同项目差异很大:可能是 IDL、OpenAPI、GraphQL schema、protobuf、DB migration、公共库的导出符号,或以上的组合。

### 为什么单独对待

契约是并行工作之间唯一的强耦合点。其他改动撞车由 git 解决,契约撞车 git 解决不了,因为冲突发生在语义层面。

### 判定

判断一个改动是不是契约变更,问:**如果这个改动生效,有没有本仓库之外的代码需要跟着改?**

不确定的时候按是处理。误判为契约变更的代价是多走一次 spec,误判为非契约变更的代价是下游无声地坏掉。

### 生命周期

契约变更在 `projects/<repo>/contracts.md` 里有两个状态:

- **在途**:已定稿但未合入。用于你自己多任务并行时的占位
- **已生效**:已合入 master

注意:在途登记只对你自己的多任务并行有效。同事不使用这套流程,看不到你的登记,所以**外部冲突的唯一有效检测手段是 `/ddd-upstream`**,不是在途登记。不要依赖后者获得虚假的安全感。

## 四、Spec 的三层

| 层 | 精度要求 | 形式 |
|---|---|---|
| 契约层 | 精确到可直接复制,**不留白** | 接口定义、类型、schema、错误枚举 |
| 行为层 | 无歧义,但不规定怎么做 | 自然语言加例子 |
| 实现层 | **沉默** | 无 |

### 归属判断

只看一条:**开发者做了另一个选择,后果是什么?**

- 后果是别人要跟着改、或上线后难以回滚 → 写进 spec
- 后果只是代码长得不一样 → 一个字都别写

### 关于代码

spec 里可以有代码,但只能是**契约形状的代码**:接口定义、类型声明、schema、错误枚举、请求响应示例。这类东西用自然语言表达只会更啰嗦更容易误读。

**不能有实现代码或伪代码。** 三个原因:开发者会把它当成必须遵守的指令,你随手写的疏漏会被原样实现;你在审一份没被编译器和测试检验过的代码;你等于把同一件事审了两遍,而 spec 那遍保真度更低。

### 松紧的正确分配

"spec 不写实现会不会太松"的答案不是补实现细节,是**把验收标准写厚**。

**实现层松、验收层紧,是正确形状。** 验收标准要精确到:好的实现都能通过,坏的实现都过不了,但通过的路径不止一条。

这也是"实现者不判定合格"能成立的前提。验收标准如果是"功能正常",开发者不得不自己判定;如果是可执行的命令加期望结果,他就只是执行和记录。

### 校准

写完之后问:**换一个完全没参与过讨论的开发者,能否在不问任何问题的前提下,产出一份能通过验收的实现?**

- 必须来问 → 契约层或行为层有洞,补
- 读完之后基本没有决策空间 → 写进实现层了,删

### 长度

**spec 的长度应与改动的不可逆程度成正比,而不是与工作量成正比。**

一个要写两千行代码但纯内部的重构,spec 可能只有半页。一个只改三个字段但对外暴露的接口,spec 可能要一整页,因为那三个字段一旦发出去就收不回来。

## 五、偏离

**偏离指实现过程中与 spec 不一致的地方。** 这是 report 里最有价值的部分,远比"我做了什么"重要,因为后者是代码的复述。

### 分档

| 档位 | 判断 | 处置 |
|---|---|---|
| 局部 | 只影响本单元自己的代码 | 留在 report |
| 跨单元 | 后续单元实现时需要知道 | 提升到任务 `context.md` |
| 破坏性 | 让 spec 的某条前提失效 | **停止,报告给人** |

**实现者只如实记录,不判定档位。** 判定需要全局视图,而实现者只看得到自己那部分。这与"实现者不判定合格"是同一条原则。

### 要不要回写 spec

一般不要。spec 是需求文档,不是实现记录,让它跟着实现细节走会变成一份低保真的代码复述。

唯一例外:偏离改变了**对外可观测的行为**。这种情况必须更新,因为下游会感知到。

---

## 六、提升判断

信息从任务级往仓库级走,叫提升。

**默认不提升。** 每提升一条都要付出永久的维护成本,而仓库级文档的价值建立在它薄这个前提上。

### 判断标准

**这条信息对一个完全不相关的新任务有没有用?**

没有就不提升,随任务归档。归档不是删除,只是移出活跃区。

### 提升到哪一层

**这条决策是否只在一个仓库内成立?**

- 只在一个仓库内 → `projects/<repo>/decisions.md`
- 涉及多个仓库之间的交互 → `cross-repo-decisions.md`

跨仓库的那份应该很薄。它变厚是个信号,说明仓库边界可能划错了。

**不双写。** 跨仓库决策只存一份,由加载规则保证读得到,不靠复制。双写必然不一致,而且没有机制能发现。

### 追加不覆盖

决策记录是追加式的。旧决策被推翻时,追加一条新的并注明取代关系,不要改掉旧的。

理由:旧决策可能还在被别处依赖,而且"为什么当初那么定、后来为什么改"本身就是最有价值的信息。

## 七、语言

以人为读者的用中文,以机器为读者或以代码为载体的用英文。

| 中文 | 英文 |
|---|---|
| 对话、spec、report、`context.md` | 代码、注释 |
| `PROJECT.md`、`decisions.md`、`contracts.md` | commit message、分支名 |
| MR comment | |

三个例外:

1. **标识符永远英文,不翻译。** 文件路径、函数名、字段名、错误码、命令、配置项,在中文句子里原样保留。翻译会导致后续 grep 不到
2. **结构化字段的 key 用英文,值用中文。** 保证 spec 和 report 仍可被脚本处理
3. **验收标准里的命令和期望输出原样保留。** 那是给机器执行的

注意:实现者的工作语境全是英文代码,写中文 report 时容易产生中英混杂、术语半译不译。写作时以上述三条例外为准。

### 代码注释

**注释只写代码里读不出来的必要信息,用精简的专业陈述句。** 与文档那条"只存代码里读不出来的东西"同源。

五条禁止:

1. emoji 与任何装饰性符号
2. 比喻、夸张、感叹等修辞
3. markdown 强调符(`**`、`#`、列表符号等)。注释不是文档,渲染不了
4. **任何本流程的术语。** spec、单元号、report、偏离、验收项、任务槽位名、`work/` 下的路径,一律不出现在代码注释里
5. **被否决的做法与修改过程。** 只写当下的做法,不写「本来想 X 但不行」。要留就留成禁令句:`// 不要改用 X,会 Y`

第四条的理由:代码合入后被不使用本流程的同事长期阅读,而 DDD 产物是任务级的、随任务归档。注释引用它们等于留下一条永久的悬空引用,读者查无可查。

需要解释"为什么这么写"时,把理由本身写进注释,不要写它记录在哪份产物里。

### commit message 与 MR comment

**只描述最终状态。** 不写"先改了 X 又回滚"、不写"按 review 意见二次修改"、不列被否决的方案。改动是什么、为什么需要,读者要;你走到这一步的路径,git 已经记了。

## 八、不变量

以下是硬规则,不是判断题。违反会破坏正确性:

1. **有价值的产出必须落盘。** 只在对话里的结论等于不存在
2. **实现者不判定合格。** 验收标准由规划者前置写死,实现者只执行和记录
3. **实现者不能自行修改 spec。** 偏离写进 report,由人决定接受与否
4. **契约在途冲突必须停下报告**,不自行绕开
5. **仓库级文档只追加不覆盖。** 例外是 `contracts.md` 的在途段,那是临时占位
6. **人工填写的内容不被自动覆盖。** 扫描生成的文档在更新时必须保留人工补充的部分

### 三个必须停下问人的点

- 契约在途冲突
- 追加需求推翻已定稿契约
- spec 前提失效

共同点:**都会让已完成的工作作废。**

## 九、槽位名解析

任务目录名形如 `<三位编号>-<槽位名>`,例如 `001-user-export`。

**槽位名和编号都可以用来定位任务,给哪个都行。** 编号由 `/ddd-spec` 新建时自动分配(取 `work/` 与 `archive/` 中现有最大编号加一)。

解析规则,按顺序试:

1. **参数是纯数字** → 按编号匹配。不足三位左补零,`2` 与 `002` 等价
2. 参数含 `-` 开头的三位数字前缀 → 按完整目录名精确匹配
3. 否则在 `work/` 下匹配后缀为该名字的目录
4. **匹配到多个时列出全部并要求我明确指定**,不要自行挑一个
5. **匹配不到时直接说不存在**,不要猜测相近的名字。除 `/ddd-spec` 外的命令不应因为找不到而创建目录
6. 已归档的任务在 `archive/` 下,只有明确要求时才去那里找

**解析出来之后,回话里用完整目录名指代任务**,不要只回编号。编号省的是输入,不是理解 —— 你说「002」我得去查它是哪个任务,你说「002-bios」我不用查。

## 十、目录结构

```
~/ddd/
  repos.md                       # 仓库注册表:别名 → 本地路径 / 远端 / 默认分支
  cross-repo-decisions.md        # 仅跨仓库决策
  projects/
    <repo别名>/
      PROJECT.md                 # 慢变事实
      contracts.md               # 契约总账 + 在途登记
      decisions.md               # 本仓库内决策
      templates/                 # 按本仓库特化的模板实例
  work/
    <编号>-<槽位名>/
      requirement.md             # 问题与技术方案,允许模糊
      spec.md                    # 契约与验收,契约层不留白
      plan.md                    # 单元划分,权威范围是"有哪些单元、哪些还有效"
      context.md                 # 仓库理解 + 本任务内已确立的事实 + 参考文档索引
      reports/                   # 权威范围是"哪些单元做完了"
      review.md                  # /ddd-review 产出
      docs/                      # 其他一切文档,须在 context.md 登记
  archive/
```

**三层职责**:`projects/<repo>/` 是仓库长期档案,`work/<task>/` 是任务临时工作区,顶层只放跨仓库的东西。

本目录独立于所有业务仓库,不进任何业务仓库的版本控制。

## 十一、产物模板 base

**只有 `/ddd-init` 需要读取它**,用于生成 `projects/<repo>/templates/` 下的特化实例。其他命令直接读取仓库已有的模板实例,不需要读 base。
