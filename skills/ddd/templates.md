# DDD 产物模板 base

本文件供 `/ddd-init` 读取,用于生成 `projects/<repo>/templates/` 下的特化实例。
其他命令不需要读取本文件,直接使用仓库已有的模板实例。

概念定义见同目录 `SKILL.md`。

## 特化的含义

把抽象描述替换为该仓库的具体事实。例如契约变更那节,base 里写"精确到可直接复制",
特化后补充"本仓库契约面为 idl/*.thrift,新增字段需标注 field id 与 optional 属性"。

**结构不变,内容变。** 特化不应增删章节。

## 通用要求

模板的每一节需说明三件事:这一节回答什么问题、什么情况下该省略、写到什么精度。

**不该有内容的节要允许省略,而不是填"无"或"暂无特殊要求"。** 否则会产生为了填满而填的行,稀释真正有内容的部分。

## requirement.md

回答「要解决什么问题、为什么这么解」。**允许模糊、允许有待确认项**,这是它与 spec 的根本区别:它是收敛过程的载体,spec 是收敛结果。

需求已经明确且改动很小的时候,本文件可以写得很短,但不建议完全跳过。它是我确认 agent 理解正确的最便宜的检查点。

| 节 | 回答什么 | 精度 | 可省略 |
|---|---|---|---|
| 问题 | 现状是什么样,为什么不行 | 讲清楚痛点,不谈方案 | 否 |
| 目标 | 做成之后什么变了 | 可判断达成与否 | 否 |
| 非目标 | 明确不解决什么 | 逐条 | 无边界争议时可省 |
| 技术方案 | 打算怎么改这个系统,为什么;考虑过并否决了什么 | 见下方边界说明 | 改法唯一且显然时可省 |
| 待确认 | 还没定的问题 | 逐条,写清楚谁来定 | 全部确定后清空 |
| 来源 | 需求出处 | 链接或出处说明 | 我口述的需求可省 |

### 技术方案一节的边界

**该写:** 系统改造的形状。新增一层还是改造现有的、同步链路还是异步、这个能力放哪个服务、涉及哪些模块和它们之间怎么衔接、以及为什么这么选、否决了什么替代方案。

否决方案写成**结论句**:「不采用 X,因为 Y」。不写选型过程、不写自己先后想过几版。

这类内容的特征是**它决定了会有哪些契约、会拆出哪些单元**,所以必须在 spec 之前定下来。它是实现者的前提,不该被实现者推翻。

**不该写:** 用什么数据结构、怎么分函数、缓存放哪、循环还是递归。这些留白,由实现者在具体上下文里决定,由 `/ddd-review` 审。

**判断边界:** 写下去会不会变成一条实现者必须遵守、但在具体上下文里可能是错的指令?会,就别写。

**注意归属:** DB schema 具体怎么改属于契约,写进 `spec.md` 的契约变更一节,不写在这里。具体改动哪些路径属于 `plan.md` 的范围字段。这里只讲形状和理由。

### 两条注意

- **产品已提供需求文档时,用自己的话重述,不要复制粘贴。** 重述才有校验价值。原文档记链接,不抄内容
- 技术方案里被否决的替代方案及理由,是 `/ddd-sync` 的高质量提升候选。那类信息代码里读不出来

## spec.md

| 节 | 回答什么 | 精度 | 可省略 |
|---|---|---|---|
| 背景 | 为什么要做 | 一两句,让人理解动机即可 | 否 |
| 契约变更 | 改了什么会让别人跟着改 | **精确到可直接复制,不留白** | 无契约变更时可省 |
| 行为 | 输入输出对应关系、边界条件、错误时的可观测行为 | 无歧义,不规定实现 | 否 |
| 明确不做 | 范围边界 | 逐条列举 | 否(防范围蔓延,通常最该写) |
| 验收 | 怎么证明做完了 | **可执行:命令 + 期望结果** | 否 |
| 变更记录 | 定稿后契约或行为发生了什么**对读者有影响的**变动 | 时间、改前改后、原因 | 无此类变动时无此节 |

变更记录只登记已在读这份 spec 的人必须知道的契约/行为变动。措辞调整、思路修正、被否决的写法,**就地改掉,不留痕**。

## report.md

| 节 | 回答什么 | 注意 |
|---|---|---|
| 做了什么 | 改动概述 | 简短。代码里读得出来的不要复述 |
| 与 spec 的偏离及原因 | **最重要的一节** | 见下 |
| 契约变更 | 实际发生的契约改动 | 与 spec 声明不一致时必须指出 |
| 验收执行结果 | 逐条列出验收项与实际结果 | 如实记录,包括失败项。不判定是否合格 |
| 遗留问题 | 已知但本次未处理的 | 说明为什么不处理 |

关于偏离一节:

- 它是主 agent 更新世界模型的唯一依据,比"做了什么"重要得多
- **没有偏离时写"无"是合法且常见的。** 不要为了不显得敷衍而硬找东西写
- 有偏离时要写清**影响范围**,但不判定档位
- 偏离不是错误。发现更好的做法、发现 spec 不可行,都属于偏离,如实记录即可

## context.md

任务对世界的理解,允许不完整、允许过期,随任务归档。

| 节 | 内容 | 写入者 |
|---|---|---|
| 涉及仓库 | 本任务关联的仓库别名与关注路径范围 | `/ddd-spec` 建立,后续可扩充 |
| 仓库理解 | 本任务范围内对既有代码的理解 | `/ddd-spec` 和 `/ddd-upstream` |
| 本任务内已确立的事实 | 从 report 偏离中提炼的、后续单元需要遵守的约定 | `/ddd-run` |
| 参考文档 | `docs/` 下所有文档的索引 | 谁写文档谁登记 |

第三节是 report 偏离信息的**提炼层**,回答"现在是什么样",不是历史记录。

- 每条标注来源单元,便于追溯
- 被后续单元推翻的直接修改或删除,历史留在 report 里
- 它的存在使得追加需求和后续单元**不需要读全部 report**。report 是追加式历史,里面可能有互相矛盾的陈述且没有标记说明哪条还成立;`context.md` 只保留当前仍然成立的部分

### 参考文档一节的格式

`docs/` 下每份文档一行。**不登记的文档等于不存在**,没有命令会发现它。

```
| 路径 | 用途 | 覆盖的代码路径 | 基线 | 产出者 |
```

| 列 | 写什么 | 为什么需要 |
|---|---|---|
| 路径 | 相对任务目录,如 `docs/reference_1.md` | |
| 用途 | 一句话。想知道什么的时候该翻它 | 决定要不要读全文 |
| 覆盖的代码路径 | 该文档描述了哪些代码。无对应代码填 `-` | `/ddd-upstream` 粗筛用 |
| 基线 | 形如 `api-service master@a1b2c3d / 2026-01-15` | 过期检测用。无代码依赖的填撰写日期 |
| 产出者 | `人` 或单元号如 `T3` | `/ddd-review` 定阅读次序用 |

后三列不是装饰,各自被一条命令消费,漏填会让对应机制失效。

指向任务目录之外的文档(历史遗留、外部资料)同样登记,路径写清楚即可。
